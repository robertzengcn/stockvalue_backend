# Milestone v1.0: MVP

**Status:** SHIPPED 2026-05-01
**Phases:** 1-4
**Total Plans:** 15

## Overview

Fix the broken M-Score fraud detection by calculating real indices from actual financial data, then layer on caching for performance, build the RAG pipeline for annual report analysis, and establish comprehensive test coverage. Tests accompany each phase rather than being a separate phase.

## Phases

### Phase 1: M-Score Real Calculation

**Goal**: Users receive accurate M-Score fraud detection results calculated from actual financial data, not hardcoded defaults
**Depends on**: Nothing (first phase)
**Requirements**: RISK-01, RISK-02, RISK-03, RISK-04, RISK-05, RISK-06, RISK-07, RISK-08, RISK-09, RISK-10
**Plans**: 2 plans

Plans:
- [x] 01-01: Data Layer Extension — IndexAuditDetail audit trail model and 6 real M-Score financial fields replacing 8 hardcoded index lines across all data sources
- [x] 01-02: M-Score Calculation Pipeline — Real Beneish M-Score calculation with 8 computed indices, per-index audit trail, and integration into risk analysis pipeline

### Phase 2: Redis Cache Integration

**Goal**: External data responses are served from Redis cache with appropriate TTLs, reducing API latency and protecting upstream rate limits
**Depends on**: Phase 1
**Requirements**: DATA-01, DATA-02
**Plans**: 2 plans

Plans:
- [x] 02-01: Cache Infrastructure — Redis cache wired into FastAPI lifespan with graceful degradation, get_cache dependency, and versioned cacheable wrapper with cached_at metadata
- [x] 02-02: Service Integration — Redis caching for all 6 data-service methods with TTL-based expiry, versioned keys, and graceful degradation

**Goal**: Users can upload annual report PDFs and retrieve semantically relevant passages with source page references, enabling document-backed analysis

## Milestone Summary

**Key Decisions:**
- Decision: Audit trail uses frozen Pydantic model (IndexAuditDetail) for immutability — Good
- Decision: AKShare field mapping uses multi-level fallback with Chinese field name as secondary — Good
- Decision: Redis cache uses graceful degradation (works without Redis) — Good
- Decision: Versioned cache keys to allow invalidation without data loss — Good
- Decision: RAGConfig uses frozen dataclass with 16 fields, singleton pattern — Good
- Decision: Parent context fetched from Qdrant by parent_id (not PostgreSQL) for simpler MVP — Good
- Decision: Upload endpoint returns immediately with status=processing, uses BackgroundTasks — Good
- Decision: Document context from RAG retrieval returned in ApiResponse meta field — Good
- Decision: Qdrant health check in lifespan uses graceful degradation — Good
- Decision: skip_if_no_db custom pytest marker for integration test DB skip logic — Good

**Issues Resolved:**
- Fixed broken M-Score fraud detection (hardcoded 1.0/0.0 defaults replaced with real calculations)
- Redis CacheManager existed but was never wired into services — now integrated with TTL policies
- RAG module was scaffolding only — full pipeline built with PDF processing, embeddings, vector search
- Low test coverage addressed — 100+ tests achieving 80%+ across all services

**Issues Deferred (to v1.1):**
- Multi-agent orchestration (LangGraph coordinator + domain agents) — Phase 5
- Analysis persistence integration (agent output -> PostgreSQL with narrative) — Phase 6
- Database credentials hardcoded in db/base.py (security issue)
- AKShare field name stability — pin version and validate schemas
- FCF CapEx sign convention differs between data sources — normalize in client layer

**Technical Debt Incurred:**
- Some RAG defaults are hardcoded (can be made configurable later)
- Embedding client uses OpenRouter API (could be local bge-m3 model for production)
