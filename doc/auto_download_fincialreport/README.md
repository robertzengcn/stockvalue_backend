# 自动下载财报 PRD 技术建议

以下建议基于 `doc/auto_download_fincialreport/auto_download_fincialreport.md`，并结合当前项目已采用技术栈（Python 3.12、FastAPI、PostgreSQL、Redis、Qdrant、PyMuPDF、AKShare/efinance）给出，目标是最小改动、最大复用。

## 1) 总体方向：从“下载器”升级为事件驱动流水线

建议采用异步事件驱动架构，而非单点“下载 PDF”功能：

- `Scheduler`：按时间策略轮询公告源
- `Watcher`：按市场/来源抓取公告元信息
- `Downloader`：下载 PDF 并做去重校验
- `Processor`：PDF 解析、结构化、关键表提取
- `AI Engine`：触发 M-Score/F-Score/DCF/利差等分析并更新 RAG
- `Notifier`：向前端推送分析完成通知

关键要求：

- 全链路幂等（重复投递不重复入库/分析）
- 状态机驱动（`PENDING -> DOWNLOADING -> PARSING -> ANALYZING -> DONE/FAILED`）
- 下载、解析、分析解耦，分别重试

## 2) 监控与抓取选型（对应 PRD 4.1/5）

优先级建议：**官方/公开 API > 轻量 HTTP 抓取 > 浏览器自动化兜底**。

- A 股：优先 AKShare 封装能力与巨潮公开接口
- 港股：优先 HKEX 披露接口
- Playwright：仅作为被限流/反爬后兜底，不建议默认主路径

原因：

- 浏览器自动化成本高、并发低、运维复杂
- API/HTTP 路径更稳定、可控、可测试

## 3) 队列与调度（对应 PRD 5）

当前项目已有 Redis，建议优先轻量方案：

- 调度：`APScheduler`（或 Arq 自带 cron）
- 队列：`Arq`（asyncio 友好，简单，适合当前规模）
- 状态持久化：PostgreSQL 任务表 + 审计字段

不建议一期直接上 Celery + RabbitMQ，除非任务规模和团队运维能力都已明确需要。

## 4) PDF 解析策略（对应 PRD 4.2/5/7）

当前代码已存在 `rag/pdf_processor.py`，并已使用 PyMuPDF 做：

- 文本块提取
- 表格检测与保留
- Parent/Child chunk 切分

建议扩展为“两阶段解析”：

1. 普通路径：PyMuPDF 文本/表格提取（低成本快路径）
2. 兜底路径：当文本提取异常或疑似扫描件时触发 OCR（如 PaddleOCR）

再结合“关键页优先”策略：

- 先定位“合并资产负债表/利润表/现金流量表”等页码
- 对关键页做高精度解析，减少全量 OCR 成本

## 5) 存储与数据模型（对应 PRD 4.2）

建议把“原始文件存证”和“分析结果”彻底分离：

- 原始 PDF：本地对象存储路径（MVP）或 MinIO/S3（中期）
- 元数据：PostgreSQL（文档来源、哈希、版本、状态、错误信息）
- 向量数据：Qdrant（结构化后的 chunk）

建议新增核心表（示意）：

- `notices`：公告主表（唯一源 ID、ticker、标题、公告日期、全文/摘要、状态）
- `documents`：文件表（url、sha256、storage_path、mime、size）
- `pipeline_jobs`：流水线任务表（阶段状态、重试次数、错误栈、耗时）

## 6) 去重与版本管理（对应 PRD 4.1）

去重不建议只靠 URL，应采用组合策略：

- 主键去重：公告源唯一 ID
- 内容去重：`sha256(pdf_bytes)` 或规范化后文本哈希
- 业务去重：同一 `ticker + report_type + fiscal_year + period`

摘要版与全文版处理：

- 摘要先到：可先入库为 `WAITING_FULL`
- 全文到达：升级覆盖分析，保留摘要版历史记录

## 7) 推送与前端联动（对应 PRD 4.3/6）

一期建议采用简单可靠通道：

- 后端到前端：SSE（适合单向状态推送）
- 站内消息/邮件：异步通知
- WebSocket 可在后续需要双向交互时再上

关键是保证“分析完成可感知”，而非先追求复杂实时框架。

## 8) KPI 落地建议（对应 PRD 6）

把 KPI 转成可测工程指标：

- 时效性：`公告发布时间 -> 分析完成` P50/P90/P99
- 解析成功率：按“关键报表字段可提取率”衡量，不只看文件成功下载
- 推送转化：通知发出后 24h 的访问/点击率

建议同步建设小型基准集（20-30 份代表性年报）做回归测试，避免解析策略升级后质量回退。

## 9) 风险与工程对策（对应 PRD 7）

- PDF 格式突变：引入解析质量评分与 OCR 自动降级
- 财报季拥堵：限流 + 重试 + 指数退避 + 队列削峰
- 数据源变更：Watcher 层适配器化，降低单源耦合
- 合规与审计：保留原始 PDF、处理日志、版本链路

## 10) 分阶段实施建议

### Phase 1（先跑通闭环）

- A 股单源监控（API/HTTP）
- 下载 -> 解析 -> 分析 -> 入库
- 基础状态机与失败重试

### Phase 2（扩展规模）

- 港股源接入
- OCR 兜底
- 更完善的去重与版本管理

### Phase 3（用户可感知价值）

- 关注列表
- 分析完成推送
- 历史 5 年版本对比视图

---

最终建议：先追求“稳定闭环 + 可审计 + 可重试”，再逐步优化“超低时延与复杂自动化”。对当前代码基线而言，这是风险最低、收益最高的路线。
